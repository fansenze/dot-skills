# Integrated task startup

This is the canonical agent workflow for installing, starting, or resuming Manage Dot Tasks with Feishu. It belongs to this skill, not a separate workflow skill. Read this before setup; use [connectors.md](connectors.md) for the transport protocol and [scheduling.md](scheduling.md) for execution/recovery. Repository editing and synthetic tests do not activate it.

## Interpret intent, then fill only real gaps

The user supplies outcomes and scope, not implementation instructions. Carry current authorization and verified configuration forward. A request to install and start **with Feishu** includes its matching receiver and active consumer. The recommended intent below also explicitly requests periodic checks and safe recovery until stopped. Use a ten-minute platform schedule (six runs per hour) by default for that request; respect another cadence or a request to disable it. Installation, reading this skill, or a startup request without that intent does not itself authorize recurring work. Ordinary-message intake and notifications still need their own stated scopes.

Recommended first-use intent:

```text
My source Feishu config is at "/absolute/path/to/feishu.yml" on my connected computer. (This file contains no secret keys, tokens, or other credentials.)

Use $manage-dot-tasks and $feishu-message-server from https://github.com/fansenze/dot-skills to install and start task management and the Feishu service on dot. Use $manage-dot-tasks as the workflow entry point, and follow its startup, periodic check, and safe recovery procedures until I explicitly stop them.

Process every message this bot receives to manage my existing and new dot/Codex tasks through natural language, with completion notifications sent to the originating Feishu chat. Notify me here in dot after verified startup.
```

The path identifies the configuration source; the prompt explicitly selects dot hosting and authorizes copying that selected configuration to dot for setup. A minimal YAML file has quoted, nonempty `app_id` and `app_secret` strings; `brand` defaults to `feishu`. Use the internal Library skill to upload the selected file from its computer, materialize it on dot, and verify its exact bytes before using the dot-local path. Preserve the file unchanged throughout transfer. This request authorizes all-sender intake for the selected bot. Record provenance on each actual request without a separate identity exchange; no sender ownership proof is required for admission.

- This explicitly scopes intake and disclosure to the user's dot/Codex tasks, including future tasks. Discover at most 10 recently updated active tasks from that set with actual tools and bind source identities; it is not a grant for unrelated records. Use `--tasks all` only if all current and future records in the selected ledger are within this authorized category. Otherwise resolve selected IDs and ask about any unresolved scope; never expose unrelated ledger entries for convenience. Record partial discovery, and do not call the initial snapshot complete when sources are unavailable.
- Configure `--mode agent --all-senders --commands query,create,continue --allow-new --updates --format card` and the resolved existing-task scope. No per-sender grant is needed. Once an actual request records the notification destination, add a native-card watch for the same authorized task scope, `--events completed --language zh`. After the receiver, active consumer, and requested periodic checks pass the acceptance gate below, notify the user briefly in dot. An unknown destination does not block startup; never request a seed message solely to finish startup. Notification overlap rules in [connectors.md](connectors.md) prevent a watch plus associated update from duplicating the same task event at the same route/format; decision replies remain separate.
- The new-task-only variation authorizes no pre-existing tasks: use `--tasks none --all-senders --allow-new --updates --mode agent --format card`, omit the independent watch and initial overview, and accept query/continue only for tasks subsequently associated with this grant. If only selected existing tasks were requested, use their resolved IDs, not all.
- If the request omits existing-task scope, continue local setup and ask one focused choice: “Only new tasks from this chat, or which existing tasks too?” Do not silently choose all. If ordinary-message intake or notifications were not requested, leave them off.
- Reuse the selected account/brand/configuration and recorded message provenance. With [all-sender intake](connectors.md#intake-without-a-binding-message), a missing sender or destination before any real request is expected and does not block startup. Keep consuming and process each actual request directly; its metadata records who triggered it and where to reply. Ask only for missing configuration or task scope, never a binding code, seed message or “sent” confirmation.
- Honor the user's Feishu service host and task executor as separate choices; configuration location determines neither. Keep the task store at its verified location. If its location or a requested environment is unavailable, report the blocker rather than silently moving work.
- On resume, reuse the existing verified store, connection, grants, policies, receiver and bridge task. “Resume with the existing scope” does not widen grants or re-enable something the user revoked. Read current state first; do not manufacture new IDs to sidestep a changed or disabled binding.

Procedural defaults are native cards, matching-instance reuse, dependency setup in the owning environment, stable IDs, bounded active calls and conservative recovery. They are not extra permission. Task actions still use actual dot tools and normal action-specific approval.

## Select the service environment and runtime

Resolve three facts separately: the requested Feishu service host, the configuration source, and the task executor/store. If service location is not explicit or already verified, ask before starting a receiver. A Mac configuration path alone never authorizes Mac hosting.

| User selection and available evidence | Route and prerequisite |
| --- | --- |
| Service on dot; configuration already readable on dot | Use the dot Feishu CLI and direct adapter; no Mac worker or transfer |
| Service on dot; configuration exists only on a connected computer | Transfer the selected file through the internal Library skill, verify its exact bytes on dot, then use the dot-local path for direct setup |
| Service explicitly hosted on a connected computer; ledger on dot | Use Remote Config Bridge once; retain credentials/transport on that host and the ledger on dot |

The user's request to use the selected configuration for dot hosting supplies the transfer scope. Follow the Feishu skill's Library handoff recipe; reuse confirmed transfer results and continue setup without requesting the same authorization again.

Before setup or reuse, resolve the requested repository revision or trusted export manifest and compare it with the actual installed code. An installed skill name, package version or current chat instructions alone do not establish that its scripts are current. Record the selected revision/digest and absolute `TASK_SKILL`, `FEISHU_SKILL`, and (only for bridge hosting) `DOT_BRIDGE`/`LOCAL_BRIDGE` roots. Use those same roots for checks, dependency setup, adapter settings, receiver startup and later batch commands; never read a current SKILL.md and execute a stale default installation. If a requested update cannot be verified or installed through the supported workflow, report that blocker before activation. Preserve the old store, pending receipts, disabled grants and receiver evidence; changing runtime roots/bindings requires an explicit reviewed transition, not a silent rebind or duplicate receiver.

For Feishu dependency setup and repository checks, prepend the verified pnpm 11.27.0 installation's `node_modules/.bin` (or verified shim directory) to `PATH` and verify that a Node child process resolves the same version. Calling the correct `pnpm.cjs` in the parent does not control a child's `pnpm` lookup. Carry the same `PATH` into every later tool call; stop on mismatch. The Feishu skill's `references/remote-configuration.md` provides the executable toolchain check. Task/bridge runtime still require only Node built-ins.

## Prepare and bind once

1. Locate the complete task skill and message server at the verified runtime roots. Explicitly read `$FEISHU_SKILL/SKILL.md` from the same pinned revision before the transport steps; keep Manage Dot Tasks as the workflow entry point and use the Feishu instructions within this orchestration, not as a second independent setup. The repository contains `skills/messaging/feishu-message-server` and `skills/messaging/remote-config-bridge`; the combined export contains all three as siblings. If the catalog is incomplete, inspect relevant `.agents/skills` in the authorized repository. **Route by the requested service host:** dot hosting continues with direct setup only after its dot-local configuration is available. For explicitly requested computer hosting, follow remote-config-bridge's `references/orchestration.md` through one verified local task. That task invokes the pinned Feishu CLI directly, never recursively invoking its setup skill. On dot register the pinned bridge `scripts/adapter.mjs` with only `{store,authorization_ref}` settings and pump its exact batches/receipts via actual `cloud_threads.create`/`send_message`/`read` tools. These tools are called by the active agent, never Node. Do not continue the direct-adapter setup below with a remote path. The remaining direct steps run on the selected service host; bridge orchestration keeps the same task policy and receipt contracts.
2. Initialize/reuse the selected external task store and follow `first-use.md` for authorized platform memory. For a computer-local configuration used by a dot service, complete the Library transfer and byte verification first. On the selected service host, reuse its readable configuration path and private state directory; the pinned `feishu.sh check --config FILE` and `identity --config FILE` inspect it without networking. Use the actual received path on dot, not the source path on another computer. Keep configuration contents in the file; task settings store its path.
3. Run `feishu.sh capabilities`; require protocol 1 and only the capabilities used by the requested policies (see the [capability matrix](connectors.md#adapter-interface-and-schemas)). Resolve the actual app ID/brand and reuse verified intended chat/sender/tenant evidence when available. Server identity verifies configuration selection, not the recipient. For all-sender intake, no sender/chat ID is required before activation: record them on actual requests. Never select an arbitrary newest inbox record or infer ownership from a name. Ask only for missing or ambiguous configuration/permissions/scope.
4. Write a private nonsecret settings JSON outside the skill: `{"server":"/absolute/feishu-message-server/scripts/server.mjs","config_ref":"/private/config.yml","state_dir":"/private/feishu-state","account_id":"verified-app-id","brand":"feishu"}`. These five keys are the only Feishu settings. Config path is a pointer; the task store never copies credentials. Preserve the config's lifetime for later sends. Credential persistence beyond the requested lifetime needs actual user authorization.
5. Register/reuse `connect` and one requested `allow-inbound --mode agent --all-senders` policy using the [connector recipe](connectors.md#intake-without-a-binding-message). Select the bot account, allowed task scope and notification behavior once. Anyone whose message reaches this bot enters that scope; sender/tenant/chat IDs are provenance, not admission filters. Open intake takes precedence over old per-sender grants for new messages without mutating them, and cancels obsolete pending challenges for the same connector/account. Add a requested independent watch only when its destination is known; do not delay task processing for it. Reuse the same policy ID and cutoff on restart, preserve pending receipts, and do not re-enable a disabled policy implicitly. `--initial` queues at most one overview per watch ID.
6. If receiver startup is authorized, reuse a matching live server on the selected host (verified runtime/config/account/brand/state directory and current lifecycle evidence), or start the pinned runtime in that environment's supported process session. Do not duplicate or restart a healthy receiver or start one on the configuration-source computer by inference. Connection readiness requires `transport_connected`/`transport_reconnected` without a later disconnect/stop; PID/config/capabilities alone do not prove readiness. Record the session handle. A receiver is needed for new inbound messages, not for an outgoing send or local scheduling.
7. Make one bounded initial `taskctl start` call and collect its result before proceeding to step 8. Do not enter an endless re-arm loop before the requested platform automation exists. All-sender intake atomically records sender/tenant/chat/message metadata and queues that same real request for agent processing. It creates no per-sender binding. The receiver alone does not process tasks. No challenge, confirmation exchange or second task message is needed. `start` reads allowed inboxes, sends outbox entries, and returns claimed agent-mode `messages` alongside a scheduler `batch`. Interpret and record messages using the [fenced decision protocol](connectors.md#agent-decisions-and-recovery); schedule authorized create/continue work before intake acknowledgement. For the scheduler batch, use actual tools with `begin → record → ack`, then finish this initial cycle. On yielded process handles, collect output until completion. A receive gap ends the current cycle visibly; inspect it before looping again. A source limitation must not trigger an unbounded error loop.
8. For requested periodic checks/recovery, first create and verify the platform automation as described below; only then enter continuous bounded consumer re-arming. While waiting for the real scheduled invocation, keep consuming and report verification pending. Complete the startup acceptance gate before the final startup confirmation in dot. Without recurring authorization, continue only the requested foreground consumer. Track separate readiness: local store, active consumer call, server connection, recorded recipient (or awaiting the first real request), notification policy, inbound grant, source coverage and platform memory; report any actual blocker or limitation rather than claiming success. Complete independent local work when messaging is unavailable. Neither startup nor a known recipient authorizes an extra test send.


## First-use and restart checkpoints

Before creating anything, inspect `connections`, `inbound`, `outbox` and `queue`, any known `handshake-status SETUP_ID`, plus a bounded read-only view of the selected store's `integration.json` connection/watch/grant/setup metadata (including enabled flags, scopes and original cutoffs); never edit it directly. Inspect verified receiver/bridge evidence too. Re-register only identical enabled bindings when useful; reuse their exact IDs and original cutoff. Changed settings/scope require an explicitly authorized replacement, never silent rebinding. Repeating setup must not create another initial overview, inbound grant, watch, receiver, bridge task, or memory convention. Preserve pending/unknown receipts and recorded message decisions.

For initial discovery, inspect at most one recent page per authorized source and read details for at most 10 recently updated active tasks in total (`queued`, `executing`, `blocked`, `awaiting_verification`). Prefer source-side active filters and a limit of 10 when supported. Do not query archives, paginate history, or read full conversations to fill the list; fewer than 10 is fine. Bind stable source identities, record partial/unavailable coverage with `coverage`, and reuse bindings on resume. This discovery limit does not change the authorized grant/watch scope.

After each bounded `start --consumer dot-active --timeout-ms 30000` call, collect yielded tool-session output. Handle returned messages with this skill's natural-language decision protocol; handle scheduler work with `begin → actual tools → record → ack`. Persist decisions/results before acknowledgements. Re-arm after a normal idle timeout while the requested active run continues. On a gap, unavailable environment or persistent source error, preserve the checkpoint, explain the affected blocker and continue independent authorized work instead of spinning. After recovery, reconcile existing intents and late receipts before issuing a new effect. Stop on the user's stop request. Loss of active execution ends that consumer; only a verified, still-authorized platform schedule can later resume it. Node itself cannot wake dot.

Report only useful readiness changes, keeping local ledger, memory persistence, active consumer, receiver connection, identity/grant, source coverage and send API acceptance distinct. A PID is not connection evidence; an API receipt is not human reading. Never add a test send as a setup side effect.

## Same-session direct startup on dot

Separate exec calls can share files without sharing localhost or PID namespaces. For this Linux-only workflow, use Node.js and util-linux `/usr/bin/flock`, a fresh dedicated receiver `state_dir` on first enrollment, and one foreground managed session. Recovery of that enrolled service uses its original settings, receiver state and task store, never a fresh empty directory. The existing settings file still has the same five fields; do not copy or inspect unrelated configuration or old receiver state. This is the startup path for new managed services, not an upgrade or adoption flow.

```bash
node "$TASK_SKILL/scripts/managed-session.mjs" --store "$STORE_DIR" --settings-file "$SETTINGS_FILE"
```

The agent context that receives the platform scheduled invocation must itself create and retain this managed session. A child agent's tool-session number is not a transferable handle: an inaccessible handle in another agent does not prove the receiver stopped. Keep session creation, periodic checks and consumption in the same owning agent context; do not add cross-agent handle forwarding.

Keep the tool session and stdin open. The entry point acquires a private stable `managed-session.flock` file and starts its receiver with the same locked descriptor inherited as FD 3. The lock is never deleted or replaced. If only the supervisor dies, its surviving receiver still holds the lock and a replacement is blocked. If all prior participants have exited, the next supervisor may acquire the lock, validate and remove only known transient endpoint/PID-lock artifacts, then start one replacement. It preserves the inbox, receipts and task store. Unexpected files or failure to acquire the lock are blockers; never kill a PID read from another namespace or remove a stable lock to bypass them. A response timeout is not proof of death.

After `ready`, write a JSON line such as `{"id":"check-1","operation":"check"}` to that same tool-session handle. Its matching `result` reports `ok: true` only when the existing receiver health command reports connected. Repeated checks reuse the receiver. Explicit task commands retain the existing form: `{"id":"cycle-1","args":["start","--consumer","dot-active","--timeout-ms","30000"]}`. Collect the matching result; the active agent interprets messages and invokes actual platform tools. Unknown command or send outcomes must be reconciled through existing receipts, never replayed automatically or assigned a fresh key.

## Periodic checks, recovery, and stopping

For the explicitly requested periodic-check/recovery workflow, the owning dot uses actual platform automation tools to create and verify **one enabled ten-minute schedule** for this new service instance. In this validation, the current scheduling interface rejected an unbounded five-minute schedule with a six-runs-per-hour limit; do not generalize this observed interface limit to every platform or extrapolate support from a finite-count test schedule. The production schedule repeats indefinitely until the user explicitly stops it, with no `COUNT`, `UNTIL`, or other automatic expiry; isolated test automations are manually disabled after acceptance and their limited lifetime is not a production default. Actual creation and saved-state verification remain authoritative. Reuse its exact automation ID on repeated setup; inspect the actual saved schedule, timezone, frequency, scope and enabled state before reporting it enabled. A missing `next_run_time` is not failure if the platform does not expose it; record that limitation and use an actual scheduled invocation as timing evidence. If the platform cannot support that cadence, report the limitation and resolve an alternative with the user. Do not substitute a Node timer, detached loop, fake platform API, model call, or ledger schedule. Local `taskctl schedule` work is not this platform automation.

For a fresh instance, establish one owning service-task context before scheduling: reuse the actual current task/thread when it owns this service, or register/reuse one service task in the selected ledger with a stable source identity. Do not require a pre-existing service record on first installation. Record which context owns the run and use its latest stop/cancel status; do not search for or invent an unrelated service task. Keep the pinned runtime roots, store/settings paths, current live tool-session handle, pending command IDs, authorization reference and automation ID in that existing context. The automation points to that context and this workflow, without copying credentials, messages, or private task contents into its prompt. A replacement session must update that context before another check. This is for new instances of this revision only, with no adoption, migration or compatibility layer.

Each scheduled invocation must:

1. Read the latest user direction, the actual automation enabled state, the owning service-task/context status (including cancelled), and the current connection/grant enabled scope first. A stop/revocation overrides the startup request and any stale queued invocation. If that evidence is unavailable, do not restart or consume. Do not enable disabled grants or create a replacement automation to defeat a stop.
2. Reconcile any outstanding command before sending another. Send the fixed `check` through the retained live session and collect the matching result. Healthy means reuse, not another receiver. A timeout, inaccessible session, denied network policy, or failed cross-exec localhost request is not proof the receiver died. Never bypass a denied access route.
3. If the session is unavailable and recovery remains authorized, classify the failure using the boundaries below. For ordinary session loss without a current policy/environment blocker, use the actual execution tool to make one new foreground `managed-session` attempt with exactly the pinned settings/store; repeatedly reading the old session's `blocked` result is not recovery. The existing stable flock must be acquired before known transient artifacts can be cleared. A held lock, unexpected state, or unavailable environment is a blocker; do not delete locks, kill foreign PIDs, change hosts, or loop on restarts. Record the actual tool result and any newly returned session handle in the owning context. Preserve receipts/inbox/store. Unknown effects remain uncertain until reconciled; no fresh IDs or blind resend.
4. After a successful check or safe replacement, resume authorized **consumption**, not just health checks: collect the outstanding bounded `start` result, or issue `{"id":"cycle-<unique-id>","args":["start","--consumer","dot-active","--timeout-ms","30000"]}` through that same session. Follow the existing message decision and `begin → actual tools → record → ack` protocols, preserving IDs for recovery. Re-arm the active consumer while dot remains active. If another consumer call is already outstanding, collect/reuse it rather than duplicate it. Report a consumption blocker separately from healthy transport.
5. Keep normal successful checks quiet; report material readiness changes or actionable blockers. Do not perform an unauthorized test send. A scheduled run can wake its platform agent only as supported by that platform; it is not a guarantee the same execution session survives indefinitely.

For “stop the service” or “stop everything,” first record cancellation in the existing owning service task/context so queued callbacks see the stop. Then disable the exact automation using platform tools and disable this service instance's grant/connection through the existing CLI; verify their disabled states, end consumption, and finally close the owned session with EOF. Do not disable unrelated connections or grants. Even if a disable step fails, the recorded stop remains authoritative: report that failure and forbid recovery. A queued invocation must recheck this direction before any restart. For “stop checks/recovery” only, disable the schedule without inferring permission to stop the requested active service. Restart after an explicit stop needs a fresh explicit user request; generic inspection, install, or a stale scheduled prompt cannot revive it.

### Recovery failure boundaries

Session recovery means starting another actual tool execution with the same persisted state. It does not recreate or reset the underlying platform environment. A different network-namespace inode is not required: separate executions may share a namespace. Use the returned tool handle, lock acquisition, current readiness and a bounded consumer result as evidence; neither a namespace number nor an old `blocked` status establishes the current service state.

| Observed failure | Action and report |
| --- | --- |
| Old session ended or its handle is unavailable; no policy/environment blocker | Follow step 3 once. Lock acquisition permits replacement; a held lock prevents a duplicate receiver even if the old handle cannot be read. After `ready`, check and resume consumption through the new handle. |
| Explicit network-policy denial, including a denial returned by `write_stdin` | Stop the affected route and report the policy reason. Do not change paths, hosts, proxies, sandbox mode, network settings or permissions to evade it. A released lock does not clear a policy denial. If the user explicitly requests retry, one attempt through the platform's normal supported approval/startup path is allowed, subject to its actual approval and execution result; do not manufacture an alternate route or repeat after rejection. |
| Execution tool fails before Node starts, for example exit 101 with `bwrap: Can't mkdir parents for /root/.codex: Not a directory` | Record a tool/environment startup blocker, not a Feishu API failure. If no new handle was returned, say “no new session obtained; service code did not run.” Do not report a restart, connection, or recovery success. Preserve the original settings/store and stop identical retries until there is evidence the blocker changed or a fresh explicit retry request. |
| Environment remains blocked and no supported platform reset interface is available | Report that limit in the existing owning context. Do not invent a reset API, repair system directories/mounts/permissions, or recommend moving a dot-only service to another host. Ordinary local commands succeeding proves only that those commands can run. |

Capture the attempted action, time, returned session handle (or none), observed failure stage/code, lock evidence and next supported action without exposing configuration or messages. Prior successful receipt, an intent without a result, a later policy denial and a released lock do not establish token expiry, a fixed session lifetime, graceful shutdown or non-delivery. Keep unknown sends unknown and reconcile their original receipts; a failed replacement proves nothing about the prior send outcome. Subsequent scheduled checks may inspect current stop/authorization and blocker evidence, but must not turn an unchanged policy/environment failure into repeated launch attempts.

## Startup acceptance gate

Report readiness separately and do not call the integrated startup complete from `ready`, a PID, `init`, or a health result alone:

- Verify the requested revision and pinned runtime/store/settings, current connection lifecycle, exact enabled grants and their scope. No seed message is required.
- Collect a real bounded `start` result from the same managed session and verify the next consumer is active (or disclose its blocker). Synthetic results establish only mock consumption; without a real inbound request, actual live message handling remains untested.
- When periodic checks/recovery were requested, inspect the real enabled platform automation, its saved cadence/ID, and then observe one actual **scheduled** invocation. Verify it either reuses the owning context's live session or safely restores the same pinned settings/store after acquiring the existing stable lock, without a duplicate receiver, then collects/re-arms the consumer. Record session survival and state-preserving recovery as distinct outcomes; indefinite session survival is not an acceptance requirement. An immediate/manual run alone does not prove scheduled triggering. Until that run is observed, report “connected; periodic check verification pending,” not full startup success. If the user disables recurring checks, report that choice explicitly instead of treating the gate as silently passed.
- Use isolated synthetic fixtures for destructive recovery tests; do not kill a production receiver or send a live test message to complete acceptance. Verify safe replacement and preserved receipts locally, and label that evidence as synthetic. A platform-triggered mock test proves scheduling/session plumbing, not live Feishu recovery.
- Recovery can resume already persisted inbox messages and reconcile stored receipts. Messages not received while the receiver was offline are outside this guarantee; verify the provider's replay behavior separately before claiming gap-free delivery.
- Record actual evidence and any gap for automation, connection, consumption, scope, source coverage and platform memory. Keep the confirmation brief and distinguish these outcomes.


Prefer EOF (Ctrl-D on an empty TTY input line) for an ordered shutdown. The supervisor stops only ChildProcess objects it created and waits for them to close before releasing its descriptor. It also handles process SIGINT/SIGTERM, but a tool-level Ctrl-C can end the execution session before cleanup completes; verify the actual result rather than claiming graceful shutdown. No arbitrary kill, generic control transport, lifecycle migration, watchdog or automatic reply is added. It does not infer decisions, call platform/model APIs, change policies/cutoffs/outboxes, or retry uncertain sends. A live but unresponsive receiver or a lost session whose receiver still holds the lock can remain blocked; report that limit rather than promising automatic recovery from every failure.
