# Safe upgrade: threaded intake and completion-only views

This is a code/store migration guide, not authorization to start a receiver, inspect credentials, send messages, replay rejected input or execute tasks. Keep real stores and receiver state outside the checkout. Use the already verified paths and identity/scope from the active conversation. Never read a forbidden configuration file or scan for credentials to perform this upgrade.

## Before changing the runtime

1. Pause the active task consumer/deliver loop at a safe boundary. Keep its actual session reference. Reconcile scheduler intents and notification leases/receipts; an unknown delivery must not be retried with a new key. A running receiver need not be restarted to read old post content: the new CLI projects raw stored rows when reading the same inbox. Do not launch a second listener.
2. Preserve a consistent backup of the selected task store (including integration, scheduler, journals, inbox dedup, checkpoints, tasks and receipts). Preserve the existing receiver database/state. Do not remove or reset either. Record the old code revision and runtime roots.
3. Apply the reviewed patch to its exact base in a separate code directory, or extract the verified portable archive. Use Node 22.18+ and pnpm 11.27.0. Run `pnpm install --frozen-lockfile` and `pnpm check` in the repo, or the exported skill checks in the README. Tests are synthetic; none prove live delivery.

## Immutable connection transition

The direct adapter entry file changed. Its old connection `module_sha256` must not be overwritten in place; the binding intentionally fails preflight after code changes. Keep the old runtime available for reconciliation. Do not manually edit integration JSON hashes/routes or manufacture API acceptance.

1. After reviewing outstanding old operations, disable the old inbound grant and progress watch (`deny-inbound`, `unwatch`) before enabling the replacement. Disable the old connection with `disconnect` when it is no longer needed. Pending notices under disabled policies cancel on claim; already sent/uncertain receipts remain for investigation. Explicit old progress watches retain their event list until disabled—reusing them would retain unwanted progress broadcasts.
2. Register the new reviewed adapter under a new connection ID, using the existing verified settings paths and account. Register a new agent grant with the same verified identity and authorized task scope, an explicit cutover `--since`, `--mode agent`, and only the previously authorized query/create/continue/allow-new/updates options. Use `--language zh --reply-mode reply`. Do not register a broader scope just to regain old associations. New-key dedup namespaces do not authorize historical replay: use a cutover after the old consumer stops, retain the old checkpoint, and do not widen the cutoff to reprocess old messages.
3. New-task-only grants do not inherit tasks created under an old grant automatically. Carry forward their already authorized ledger IDs explicitly when continued access is authorized. New policy IDs do not implicitly inherit private conversation history. When the current user authorization includes continued access to old task context, pass `--context-from OLD_AGENT_GRANT_ID` (or an explicit comma-separated list of at most 20 old grant IDs) to the new grant. Each referenced grant must have the exact same account, tenant, sender and destination. This is a new, explicit authorization to use historical evidence within the replacement grant's current task scope; it never re-enables a disabled grant or restores revoked task permissions. Preserve disabled old grants as disabled. The claim can recover old task-bound original messages and API-accepted bot/watch receipts using provider parent/root/thread references, then join their unchanged ledger/Codex bindings. Old taskless clarification or approval exchanges remain excluded and require fresh clarification. New-task-only scope does not gain old tasks from this option. The option copies no inbox entries, executes no old messages, changes no cutoff/checkpoint and retries no unknown receipt. On later upgrades, list all still-authorized earlier grants explicitly; references are not inherited transitively. Do not recreate tasks by their title.
4. For existing task notifications, register a scoped watch with `--events completed --language zh`. Omit `--initial` on migration unless a new overview is specifically desired. New associated create/continue messages become threaded anchors; a watch without a current authorized anchor uses its fixed chat route. Existing notices retain their old body, options, key and destination. Do not change them to the new design for a retry.
5. Resume one authorized consumer. Inspect `start` receipt results, `receive_gaps`, `inbound`, `outbox --all`, `queue`, and `doctor`. With manual `ingest` / `message-next`, deliver the receipt acknowledgement before substantive work. Never equate `pending` with sent or `api_accepted` with human reading.

The known historical rejected rich-text request must remain in the old dedup history. This implementation request is already authorized in the main conversation; it must not be recreated by replaying that old message. Historical rejected records lack a verified failure envelope, so this upgrade does not invent a request failure or send for them. After verifying the old rejected hash against authorized conversation/receiver evidence, the agent can annotate it with `request-failure ID --stage parse --reason SANITIZED_REASON --evidence VERIFIED_REFERENCE`. This records a visible historical failure without changing the original rejected status, dedup identity or checkpoint, sending a message, creating a task, or replaying content. Do not guess which hash belongs to the user. Future authorized parse/create failures use the new request-failure records.

## Completion missing from the chat

Check these distinct stages without changing task facts to force a notification:

- The actual ledger must be `completed`, with current passing checks and completion evidence. An execution observation `completed`, a finished Codex turn, or a recorded scheduling receipt does not mark success. Keep the transition `executing -> awaiting_verification -> check -> complete` in the agent workflow.
- A matching enabled completion watch or an enabled agent `updates` grant with a recorded create/continue association must have existed when completion was committed. Routine later reads/notes do not backfill a notice. If the old completion predates the policy, do not reopen/recomplete or rerun the task to manufacture an event; coordinate an explicitly authorized scoped result reply.
- Task mutation and completion notice are committed together. If the notice is pending, an active `deliver`/`start` consumer must run. A stopped dot is not woken by Node. If preflight is dead, inspect the reviewed module pin and format/size before an authorized retry with the same payload/key.
- `api_error`, `not_sent`, and `delivery_unknown` are different. Network-policy denial is an environment blocker. Do not change proxy routes, add service permissions, restart a healthy receiver or resend unknown delivery as a code workaround. Resolve unknown only with conclusive evidence and the existing `resolve-notice` command.
- An authorized request that never became a task now has a visible failed request and a failure reply. After a task-creation error, inspect the journal/source binding/decision first; call fenced `message-fail --stage create` only when no task committed. No uncertainty about an actual external effect may be relabelled as “not created.”

## Parent-coordinated demonstration and final acceptance

Create one explicitly labelled fictional/demo task only when the parent coordinates the user's requested demonstration. A suitable title is “虚构/演示：任务通知效果”. Verify synthetic output, then complete it and inspect the actual receipt. Confirm the four labels, Shanghai seconds, original-topic reply, single-task title/ID and exactly one completion update. Run no real work or unlabelled fabricated result to populate the example.

The local artifact is a candidate for dot validation. Transfer through official Library; dot validates the closed loop and may fix it there. Synchronize those verified changes back into this same local repository, then wait for dot's final revalidation. Push is authorized only after the parent explicitly confirms that final revalidation passed. Local tests are not that confirmation.
